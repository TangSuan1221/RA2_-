## 1. 工具链逆推：顽皮狗引擎到底怎么组织"一张地图"

三层容器，缺一层都读不出来。这一节全部是 E1。

### 1.1 第一层：PSARC 归档（容器层）

`psarc2` 的 TOC 条目说明每个文件带四个量：

```
index_list_size  // 该文件占用的块表条目数
size             // 解压后大小
offset           // 归档内绝对偏移
input_size       // 压缩后大小
```

归档头另有 `block_size`（固定块大小）+ `block_sizes[]`（每块实际长度）+ `compression_type`，且 crate 依赖 `aes ^0.9.1` / `cfb-mode` —— 说明**存在加密 psarc 分支**（PS4/PS5 侧常见）。

**对关卡设计的含义（关键）**
- 块级独立压缩 ⇒ 引擎可**随机读取归档内任意单个文件，不必解整包**。这是流送（streaming）的物理前提。
- 因此"一张大地图"在磁盘上不是一个大文件，而是**一组 psarc 归档**；引擎按需挂载/卸载归档，而非按需加载整个关卡。
- `TLOU_PSARC_Tool` 能用纯文本 `FilesMap.txt` 做导入映射 ⇒ 路径表无强签名校验 ⇒ 归档重组是可行的。这解释了为什么 TLOU 的 MOD 生态能改贴图/模型而不用重签整包。

### 1.2 第二层：pak 资产（模型/贴图层）

`fmt_nd_pak` 暴露的 pak 内部结构（来自 `nd_pak.bt` 模板路径）：

```
Page[0-3] → GEOMETRY_1 → Item → Geometry → SubmeshDescs → [submesh name] → Material
```

| 硬约束 | 数值 | 对设计的影响 |
|---|---|---|
| 单 page 数据上限 | **1 MB** | 一个复杂物件会被切成多个 page；场景物件天然倾向"小而多" |
| 单 submesh 顶点上限 | **~60,000**（实测建议远低于此） | 建筑靠 submesh 拼装，而不是一整块巨型 mesh |
| LOD 层级 | **LOD0–LOD3** | LOD3 特殊：**保留用于阴影与面部光照**，不可丢弃 |
| 骨骼存放 | 独立 `*-base.pak` | 角色 pak 大多**自身无骨骼**，靠 base 骨架绑定 |
| 角色组成 | body / head / hair / jacket / holster **分属多个 pak** | 角色是"部件装配体"，不是单体文件 |
| 解包根目录 | `Actor77`、`texturedict2` … | 存在集中式贴图字典与 actor 根 |
| 贴图命名 | `<角色>_<部位>_<材质>-color.dds`，类型 color / normal / AO / transparency，BC1/DXT1 | 材质系统按通道约定固定 |

**这直接给出了"关卡是怎么拼出来的"的答案**：TLOU 的场景是**模块化 prefab 装配 + page 分包 + LOD 分级**的体系。地图作者不是在雕一块地形，而是在摆 actor。

### 1.3 第三层：DC 脚本 VM（交互层）—— 本次最有价值的发现

`dc-disassemble.py` 揭示了顽皮狗引擎的脚本虚拟机完整形态：

**文件头结构**
```c
DcHeader   { magic, unk1, reloc, unk2, unk3, defCount, defTableOff, unk4 }
DcDefinition { nameId(u32), typeId(u32), offset(u32), unk }
DcDescriptor { start(u32), _, end(u32), _ }
```

**命名系统**：所有符号名统一折成 StringId = `crc32(name, poly=0x04c11db7, init=0)`。脚本里没有字符串表，只有 hash。

**已确认的 12 个 typeId**（E1，可直接用于建模实体属性系统）：

| 类型 | typeId | 类型 | typeId |
|---|---|---|---|
| `vector` | `0x012f77fe` | `boolean` | `0x8b4e76ff` |
| `string` | `0x0b3952e7` | `vec4` | `0x93bd2e95` |
| `float` | `0x0f182ec3` | `script-lambda` | `0x9ed499e1` |
| `angle` | `0x13812cd6` | `function` | `0xab3eb31f` |
| `state` | `0x2e6743e3` | `int32` | `0xc7cb2752` |
| `direction` | `0x7194cbe7` | | |
| `color` | `0x71e73c6c` | | |

**指令集（0x00–0x4A，节选关键项）**
- `0x1B call` — 调脚本函数
- `0x1C callFf` — **调原生（native）函数** ← 通往引擎能力的唯一出口
- `0x2D branch` / `0x2E branchIf` / `0x2F branchIfNot` — 状态机骨架
- `0x13/0x14/0x15 lookup{Int,Float,Pointer}` — 按 StringId 查表取属性
- `0x16/0x17/0x18 move{Int,Float,Pointer}`、`0x43 move`
- `0x19 castInteger` / `0x1A castFloat`
- 全套 int/float 比较（`0x1D–0x26`）、位运算（`0x31–0x37`）

**辅助文件**
- `.dci` 提供 `(export sym1 sym2 …)` 导出符号表 → 脚本对外的 API 面
- `sids.txt` 提供 `hash nativeName` 映射 → 这是还原 `callFf` 目标名的钥匙

**由此可确定顽皮狗引擎的交互物模型（这是全报告最重要的一条推断，等级 E1+推理）：**

```
交互物 = 实体(Entity)
        ├─ 一组按 StringId 索引的「类型化属性」(state/vector/angle/direction/color/boolean/int32/float/string/vec4)
        ├─ 一个「触发体积」(volume) 
        └─ 一个「script-lambda」回调（typeId 0x9ed499e1）
             └─ 内部 branchIf 状态机 → callFf 调 native 能力
```

即：**"能不能交互"不在模型里，在 dc 脚本里。** 模型 pak 只提供几何与材质，交互语义由脚本层的 state + lambda 决定。这就是为什么单纯解包 pak 看不到"这是什么交互物"——必须同时解析 dc 脚本与 `sids.txt`。

## 2. 整体大地图设计（E2）

### 2.1 定性：这不是开放世界，是「线性走廊 + 章节枢纽」

TLOU 的整体地图是横跨美国的**旅程拓扑**，不是可自由漫游的连续世界。章节主线：

```
序章 Austin → Boston 隔离区 → The Slums → The Outskirts → Bill's Town
→ Pittsburgh → The Suburbs → Tommy's Dam → The University
→ Lakeside Resort → Bus Depot → Jackson（尾声）
```

结构特征：
- **单向推进 + 局部回环**：允许在一个 Level 内绕回，但不允许跨章节回退。资源管理因此是"沉没成本"，强化紧张感。
- **每章一个"安全枢纽"**（safe hub），承担补给、对话、叙事降速；枢纽向周边辐射 3–5 个战斗/探索关卡。
- **可见但不可即时抵达的远景地标**（landmark）负责保持空间连续感 —— 这正好对应 pak 体系里的 LOD3 / impostor 用法。

### 2.2 四层空间尺度（建议直接沿用的分层法）

| 层 | 单位 | 职责 | 对应引擎载体 |
|---|---|---|---|
| **Region** | 章节/州 | 主题、色调、敌人配比 | 一组 psarc |
| **Level** | 关卡 | 一条完整遭遇链 | 一个/多个 psarc + actor 组 |
| **Encounter** | 战斗碗 | 一次可解决的交火 | actor 组 + 触发器区 |
| **Prop/Cover** | 物件 | 掩体、门、可翻越物 | 单个 pak（1MB/page 约束内） |

**这个四层法比"大地图/小地图"二分更有用**，因为它每一层都对应一个真实的引擎容器边界 —— 可以直接拿来做关卡预算表。

### 2.3 节奏模板（本报告给出的可复用结论）

一个 Level 内部的时间分配近似：

- 探索/搜刮段落 **35–45%**
- 潜行/静默段落 **25–35%**
- 强制战斗段落 **20–30%**
- 叙事/过场 **5–10%**

规律：**每 2 次高压遭遇后必插 1 次低强度探索**；每次进入新 Region 的前 3 分钟不放强制战斗（先给玩家读空间）。

### 3.2 垂直通行规范（最关键的一张表）

TLOU 的潜行-战斗切换完全建立在**高度分层**上，所以这张表是整套 metrics 的核心：

| 通行类型 | 高度区间 | 行为 | 设计用途 |
|---|---|---|---|
| 直接跨越 | < 0.45 m | 无提示，自动跨过 | 地面细节，不构成障碍 |
| **Vault（翻越）** | 0.45 – 1.20 m | 有交互提示，快速翻越 | **低掩体 ↔ 移动** 的核心节奏点 |
| **Climb（攀爬）** | 1.20 – 2.20 m | 有提示，需动作时间 | 建立垂直层次、藏高处补给 |
| Ladder（梯子） | 2.20 – 8.00 m | 点按使用 | 连通不可攀楼层 |
| 不可通行 | > 8.00 m 无辅助 | — | 地图边界 |

### 3.3 掩体规范

| 掩体类型 | 高度 | 站立暴露 | 蹲姿暴露 | 备注 |
|---|---|---|---|---|
| 半身掩体 | 0.90 – 1.10 m | 上半身暴露 | 完全遮蔽 | 站立射击用 |
| 全身掩体 | 1.60 – 1.85 m | 完全遮蔽 | 完全遮蔽 | 完全安全位 |
| 可破坏掩体 | 任意 | — | — | 提供"安全位不永久"的压力 |
| 转角掩体 | — | — | — | 转角必须留 ≥0.6 m 的可探身空腔 |

**硬规则（E3，但工程上强成立）**：任意掩体周围必须保留 **≥0.8 m** 的绕行通道，否则 AI 会卡死、玩家会觉得"这掩体是假的"。

### 3.4 水平尺度规范

| 参数 | 数值 | 说明 |
|---|---|---|
| 单人通行最小净宽 | 1.20 m | 低于此值会触发碰撞摩擦 |
| 双人并行 | 2.00 m | 队友跟随时不互相挤开 |
| AI 拆队通行 | ≥2.40 m | 两名敌人并排搜索所需 |
| 标准门洞 | 0.90 × 2.10 m | — |
| 双开门/大通道 | 1.80 × 2.20 m | — |
| 楼梯 | 踏面 0.28 m / 级高 0.17 m | — |
| 战斗碗直径 | 18 – 30 m | 潜行可绕圈的最小尺度 |
| 狙击/远程视线 | 40 – 60 m | 超过此距离玩家失去空间感 |
| 视线遮挡断点间距 | 每 8 – 12 m 一处 | 保证"每拐一个弯都有新的信息" |

### 3.5 时间尺度规范

| 参数 | 数值 |
|---|---|
| 静默探索间隔 | 60 – 120 s |
| 单次遭遇时长 | 45 – 90 s |
| 潜行被发现后的反应窗口 | 1.5 – 2.5 s |
| 制作/搜刮交互时长 | 1.2 – 2.0 s（可被打断） |

### 3.6 ⚠️ 真正的 Metrics 逆向方法（比上面所有估算都重要）

**不要量整关，要量 prefab 库。** 因为 TLOU 场景是模块化装配的，所以引擎侧的标准尺寸必然**收敛在有限的一组 prefab 上**。正确流程：

1. 用 `Ekey/U4.PSARC.Tool` 解出 pak；
2. 用 Noesis + `fmt_nd_pak` 批量导入场景 pak，看 `SubmeshDescs` 的名字（门/梯/掩体通常有语义命名）；
3. 对同类 prefab 取包围盒，**做尺寸直方图** —— 直方图上的尖峰就是引擎标准值；
4. 量 20–30 个同类 prefab 即可钉死该类的标准尺寸，误差远小于逐关人工估算。

这一步是目前唯一能把上表 E3 升级为 E1 的路径。**报告第 3 节的所有数字，请用这个方法复核后再进 GDD。**

## 4. 交互物类型清单

按**引擎实现机制**分类（而非玩法分类），因为只有这样才对做游戏的人有用。每类给出：引擎载体 / 玩家侧表现 / 对撤离游戏的迁移判断。

| # | 类型 | 引擎载体（E1 依据） | 玩家侧表现 | 迁移建议 |
|---|---|---|---|---|
| 1 | **门 / 通路开关** | pak 几何 + dc `state` 机（关闭/开启/破坏三态） | 提示推开/撞开 | ★★★ 撤离点门禁核心 |
| 2 | **翻越 / 攀爬点** | pak 几何 + vault/climb 标记体 + native 调用 | 高亮提示 | ★★★ 直接采用 3.2 表 |
| 3 | **梯子 / 绳 / 升降** | 独立 pak + 使用 lambda | 点按使用 | ★★★ 垂直撤离路线 |
| 4 | **拾取 / 补给容器** | 容器 pak + 掉落表 lambda | 靠近提示搜刮 | ★★★ 结合分类负重 |
| 5 | **工作台 / 制作点** | 场景 pak + 长时交互 lambda | 进入制作 UI | ★★★ 局内改装 |
| 6 | **触发器体积（脚本区）** | 不可见 volume + `branchIf` 状态机 | 无提示，被动触发 | ★★★ 撤离区判定 |
| 7 | **过场 / 对话触发** | volume + `script-lambda` | 强制或可选 | ★★ 用于情报/委托 |
| 8 | **载具 / 移动平台** | pak + 位移驱动 lambda | 乘坐/推动 | ★★ 撤离载具 |
| 9 | **尸体 / 可搜刮敌人** | 角色 pak 死亡态 + 容器 lambda | 搜刮 | ★★★ 高风险高回报 |
| 10 | **可破坏物 / 环境击杀** | pak + 物理 + 伤害 lambda | 射击/推落 | ★★ 消耗战术 |
| 11 | **门禁 / 电路 / 发电机（谜题）** | 多实体 + `state` 依赖链 | 需条件解锁 | ★★★ 红区准入 |
| 12 | **存档 / 检查点** | volume + 存档 native | 自动 | ☆ 撤离制不需要 |
| 13 | **AI 导航标记** | cover point / patrol waypoint / sound emitter | 不可见 | ★★★ 尸潮与 NPC 生态必需 |
| 14 | **光源 / 火源** | 灯光 pak + 感知参数 | 影响潜行可见度 | ★★★ 夜间撤离必备 |
| 15 | **收集品 / 文档** | 扁平 pak + 拾取 lambda | 阅读 | ★ 叙事填充 |

**筛选结论**：15 类中，撤离玩法需要 11 类（★ 合计 3+3+3+3+3+3+2+2+3+3+3+1 = 12 项），可砍掉第 12 类（存档点）与第 15 类（收集品降级为可选）。

### 4.1 交互物的一条通用实现律（从 dc VM 反推）

因为交互语义全在脚本层（`state` + `script-lambda` + `callFf`），所以：

> **交互物 = 几何 prefab + 触发体积 + 状态机 + native 能力调用**

做自己的引擎时，只要把这四件东西拆成可数据驱动的四段配置，就能获得和顽皮狗一样的"加一个新交互物不用改代码"的扩展性。反过来，如果把交互逻辑硬编码进物件类，交互物类型数会卡在 10 个左右上不去。

## 5. 对《幸存者裂城》的可迁移与不可迁移清单

### 5.1 直接采用（高价值）

1. **3.2 垂直通行表**——潜行/战斗切换的地基，与你 GDD 的"弱点与硬直"互补。
2. **3.6 prefab 直方图法**——你自己的关卡做 metrics 规范时，同样应该量 prefab 而不是量整关。
3. **1.1 块级压缩流送**——你 GDD 里"门后/红区"的分层，物理上就该实现为**分区 psarc 式归档 + 门后预载**。这是"门后有东西但你不知道是什么"的技术底座。
4. **第 4 节 12 类交互物**——按你的 14 天周期与撤离点机制重新配权。
5. **安全枢纽辐射结构**——你的"定居点（真实地块）"正好是 hub，周边关卡是辐射关卡。

### 5.2 必须改造（不可直接照抄）

| TLOU 做法 | 为什么不能抄 | 你的替代方案 |
|---|---|---|
| 单向走廊、不可回退 | 你是 PvPvE 撤离，需要**多路径 + 环路**，否则撤离点会被单点堵死 | 每区域 ≥3 条通路径，撤离点 ≥2 个候选位 |
| 无 HUD、极简提示 | 撤离游戏需要经济信息密度 | 保留极简交互提示，但资源/负重必须显式 |
| 线性叙事节奏（2 高压 1 低压） | 你的局内时长由玩家决定 | 用"物资密度曲线"代替强制节奏 |
| 存档检查点 | 撤离制本身即存档 | 删掉 |
| 敌人 AI 以叙事为目标 | 你的 NPC 生态需要经济行为 | 在 13 类导航标记上加"资源驱动巡逻" |

### 5.3 明确不要抄

- **线性关卡拓扑**。这是 TLOU 服务于叙事的选择，与撤离沙盒的"自由路径 + 时机博弈"直接冲突。
- **固定遭遇脚本**。你的红区需要动态强度，不能是写死的 encounter。
