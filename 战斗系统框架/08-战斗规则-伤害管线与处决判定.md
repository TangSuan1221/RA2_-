## 1. 单帧伤害管线（固定 9 步，顺序不可调换）

**顺序就是规格**：③ 无敌帧与 ④ 招架必须在 ⑤ 部位修正之前，才能"该免的伤害一点都不算"，避免 UI 先闪一下掉血再回血。任何调序直接产出 F3/F4/F7。

| 步 | 阶段 | 输入 | 输出 | 失败分支 |
|---|---|---|---|---|
| ① | 命中查询：hitbox OBB 扫掠（§2）| 招式 active 窗、骨架姿态、环形缓冲 | `Contact[]`（point/dir/normal/ttc）| 无接触 → 整步返回 `null`，**不产生任何事件** |
| ② | 去重 `hitSet` | `actionInstanceId`、`victimId`、`hitboxIndex` | 是否首次 | 已存在 → `reason='dup'`，**唯一不广播事件的拒绝**（同一命中的重复查询）|
| ③ | 无敌帧 / 闪避 | `victim.iFrameUntilStep`（`CB-DODGE-IFRAME` 0→200 ms 折算 pct [0, 0.364]）| 通过/拒绝 | 窗口内 → `reason='iframe'`，广播 `damage=0`（供"擦过"音效）|
| ④ | 招架判定 | 受击方 parry 动作进度、命中时刻 | 招架成功/失败 | 成功 → 攻击者 hitstun `CB-PARRY-RIPOSTE-STUN`，受害者 **0 伤害**，仍广播 |
| ⑤ | 部位与护甲修正 | `Contact.point`、受击方骨架分区、护甲覆盖 | `hitGroup`、`mul`、`armorTaken` | 命中点不在任何分区（可破坏物）→ `mul=1.0`，走 prop 分支 |
| ⑥ | 伤害与 poise 结算 | `hb.damage/poiseDamage`、`mul`、`armorTaken`、弹药品质系数 | `damage`、`hp`、`poise` | 有 poise 者累加；`poise ≥ CB-POISE-MAX` → `stagger`（§4）|
| ⑦ | 反应选择 | `reactions.json`（dir band / heavy / poiseBreak）| `reactionId`、`hitstunMs`、`lockLowerBody`、`knockbackScale` | 无匹配条目 → 加载期即报错（10 §0 禁止兜底），运行期不可能发生 |
| ⑧ | 击退与冻帧 | `hb.knockback/hitstopMs`、受害者质量 | 速度脉冲、`hitstopMs` | 双方各写 `combat.hitstopMs`（§6.2）|
| ⑨ | 事件广播 | 以上全部 | `GameEvent`（`t:'hit'`）| 唯一出口，经 `bus.flush()`（阶段 11）出队 |

### 1.1 `resolve` 签名与伪代码

> 03 §4 未给 `resolve` 签名（只给了文件名），本章补齐；字段名沿用 03 §3.2 `CombatState` 与 03 §4.5 `GameEvent`，`HitboxDef` 取 10 §1 `hitboxes[]` 元素。

```ts
// combat/resolve.ts —— 禁 import three
export type HurtGroup = 'head' | 'torso' | 'limb' | 'leg';
export type RejectReason = 'dup' | 'dead' | 'iframe' | 'parried' | 'execLock' | 'stunInvuln';
export interface Contact { point: Vec3; dir: Vec3; normal: Vec3; ttc: number; }
export interface ResolveResult {
  applied: boolean; reason: RejectReason | null;
  damage: number; poiseDamage: number; hitGroup: HurtGroup;
  knockbackVel: Vec3; hitstopMs: number; reactionId: string | null;
  event: GameEvent;                       // 恒有；被拒时 damage = 0
}
export function resolve(world: World, attacker: Actor, victim: Actor,
                        hb: HitboxDef, contact: Contact): ResolveResult {
  const st = victim.combat;
  // ② 去重：同一 attack 实例 × 同一 victim × 同一 hitbox 只结算一次
  const key = `${attacker.combat.actionInstanceId}:${victim.id}:${hb.index}`;
  if (attacker.combat.hitSet.has(key)) return reject(world, attacker, victim, hb, contact, 'dup');
  attacker.combat.hitSet.add(key);      // 清空时机 = actionInstanceId 自增（换招），不按时间清
  // ③ 死亡与无敌帧（必须在 ⑤⑥ 之前）
  if (st.dead) return reject(world, attacker, victim, hb, contact, 'dead');
  if (world.step < st.iFrameUntilStep) return reject(world, attacker, victim, hb, contact, 'iframe');
  if (victim.execLock && victim.execLock.partnerId !== attacker.id)
    return reject(world, attacker, victim, hb, contact, 'execLock');       // §5.2 兜底
  // ④ 招架：命中时刻相对 parry 动作 t=0 判定，窗口 CB-PARRY-WINDOW = 140 ms（±70）
  if (isInParryWindow(victim, world.step)) return resolveParry(world, attacker, victim, hb, contact);
  // ⑤ 部位与护甲
  const g     = pickHurtGroup(victim, contact.point);   // head > torso > limb > leg（体积最小优先）
  const mul   = HURT_MUL[g];                            // CB-HURT-* 1.8 / 1.0 / 0.7 / 0.55
  const armor = armorTaken(victim.armor, g);             // §3.2 覆盖表，未覆盖 = 1.0
  // ⑥ 伤害与 poise
  const dmg = Math.max(CB_DMG_MIN, rint(hb.damage * mul * armor * ammoQualityMul(attacker)));
  st.hp -= dmg;
  if (hasPoise(victim)) {
    st.poise += hb.poiseDamage;
    if (st.poise >= CB_POISE_MAX) stagger(victim);        // 破防 → §4.1
  }
  // ⑦ 反应选择（dir band × heavy × poiseBreak 三键命中）
  const band = dirBand(attacker, victim, contact.dir);
  const r    = pickReaction(band, hb.category === 'heavy', st.poiseBroken);
  // ⑧ 击退与冻帧
  const kbSpeed = hb.knockback * (CB_KNOCKBACK_MASS_REF / victim.mass) * r.knockbackScale;
  applyImpulse(victim, scale(contact.dir, kbSpeed));
  attacker.combat.hitstopMs = Math.max(attacker.combat.hitstopMs, hb.hitstopMs);
  victim.combat.hitstopMs   = Math.max(victim.combat.hitstopMs,   hb.hitstopMs);
  // ⑨ 事件广播（唯一出口）
  const ev: GameEvent = { t: 'hit', attackerId: attacker.id, victimId: victim.id,
                          actionId: attacker.combat.actionId, damage: dmg,
                          point: contact.point, dir: contact.dir, heavy: hb.category === 'heavy' };
  world.bus.push(ev);
  return { applied: true, reason: null, damage: dmg, poiseDamage: hb.poiseDamage, hitGroup: g,
           knockbackVel: scale(contact.dir, kbSpeed), hitstopMs: hb.hitstopMs,
           reactionId: r.id, event: ev };
}
```

`reject()` 恒定广播 `damage = 0` 的 `t:'hit'` 事件（`dup` 除外），使表现层能对"被格挡/被闪开/被保护"给出与"打空"不同的反馈——这是 I3 公平感的必要条件之一。

## 2. 回溯命中（MontageGraph 的 Collision Caching 移植）

> 证据等级：MontageGraph README 原文列明 **碰撞数据烘焙 + 回溯扫掠（跳过帧也补检测）+ 服务端延迟补偿 + 蒙太奇链接连招** —— 机制事实 **E1**；本章改用途（从"网络延迟补偿"改为"逻辑步间连续扫掠"）与全部参数（采样数/容忍/容量）为**工程移植 E3**。

### 2.1 为什么网页端更需要它

| 事实 | 数值 | 后果 |
|---|---|---|
| 高速挥击的单步位移 | 30 m/s × `TM-DT` = **0.50 m/步** | 与 `hitboxes.size` 最短半长 0.22 m 同量级 |
| 静态 OBB 单步覆盖 | 2 × 0.22 = 0.44 m | **0.06 m 步间死角**，每步约 12% 行程不被检测 |
| 目标胶囊半径 | `CC-CAP-RADIUS` = 0.32 m | 对 Actor 覆盖升到 0.76 m；对面/可破坏物仍是 0.44 m |
| 掉帧叠加 | 20 fps 时补 3 步（`TM-MAX-CATCHUP`），第 4 步起逻辑时间被丢弃 | 逻辑时间变慢而非跳步；视觉插值 `alpha` 卡在 1.0 数帧 ⇒ 视觉与逻辑错位，玩家看到刀已过身而判定未到 |

结论：**漏判主因是"步间离散采样"，不是掉帧；掉帧只是放大它。** 网页端单线程 + GC + WebGPU 提交抖动使掉帧不可控，因此不能依赖"帧率够高就不漏"，必须在逻辑步之间自己补扫掠。

### 2.2 环形缓冲规格

| 项 | 规定 |
|---|---|
| 容量 | `CB-HIST-FRAMES` = `TM-MAX-CATCHUP` + 2 = **5 步**（覆盖一次补算突发 + 1 步余量）|
| 每条内容 | 8 个顶点的**世界坐标**（8×3 f32 = 24 float），不存旋转/位置（顶点已含全部信息）|
| 索引与内存 | `ring[step % 5]`，每 (actor, hitbox) 一条预分配 `Float32Array(24)`，零分配写入；480 B/hitbox，8 hitbox = 3.8 KB/角色，100 角色 = 380 KB |
| 写入时机 | 阶段 4 内、本方扫掠**之前**（保证本步姿态已定且不与读取冲突）|
| 首步 / 热载后 | `prev` 缺失 → 退化为静态 OBB，并 `debug.warn('hist-miss')` 计数（§8 断言读取它）|

### 2.3 扫掠检测实现要点（不需要完整 GJK）

1. **顶点线性插值**：中间帧 8 顶点 = `lerp(prevV[i], curV[i], t)`。误差来自"真实旋转 vs 顶点插值"：单步旋转 ≤ 360 °/s × 16.667 ms = 6°，弦高 `R(1−cos3°)` = 0.0014R，取 R ≈ 0.6 m ⇒ **0.0009 m**，远小于容忍 0.05 m。
2. **采样数** `CB-SWEEP-SAMPLES` = 3（t = 0, 0.5, 1），自适应升到 `CB-SWEEP-SAMPLES-MAX` = 5：`N = clamp(ceil(|Δc| / (minHalf + CB-SWEEP-TOL)), 1, 5)`，`Δc` 为 OBB 中心位移、`minHalf` 为最短半长。
3. **采样间距必须 < 有效覆盖**：间距 0.50/2 = 0.25 m；覆盖 = 半长 0.22 + 膨胀 `CB-SWEEP-TOL`/2 = 0.025 + 目标胶囊 0.32 = 0.565 m ⇒ 0.25 ≪ 0.565，**不漏判**。这是 F2 的量化消除条件。
4. **对 Actor 目标**用「胶囊段 ↔ OBB 最短距离 ≤ 半径 + 膨胀」（比 OBB-OBB 便宜且精确）；**对 prop / 可破坏物**用 SAT 15 轴（3+3 面轴 + 9 边叉积轴），关卡几何多为 AABB 时退化为 6 轴。
5. **TTC** 取最早命中采样的 `t`，**不做二分细化**：细化到 0.02 m 需 3 次额外 SAT，收益被 `CB-SWEEP-TOL` 0.05 m 吃掉；TTC 只用于反应方向与冻帧起点对齐。同一步 3 次采样命中同一 victim 时，第 ② 步 `hitSet` 只放行第一条（F3 消除点）。

### 2.4 与「60Hz 逻辑步」的关系

| 层面 | 规定 |
|---|---|
| 逻辑步 | 固定 `TM-TICK-HZ` = 60、`TM-DT` = 16.667 ms；补算上限 `TM-MAX-CATCHUP` = 3 |
| 渲染帧 | 可掉帧、可不均匀；`alpha ∈ [0,1)` 只用于插值，**不参与任何判定** |
| 命中判定位置 | **永远在逻辑步内**（§1 步骤①）；渲染帧不产生命中 |
| 回溯缓存语义 | "上一个**逻辑步**的 OBB 快照"，不是"上一渲染帧"；与 MontageGraph 的延迟补偿共享"历史碰撞体 + 区间扫掠"结构，用途不同 |

## 3. 部位与护甲（对接 GDD §3.2 弱点设计）

### 3.1 hurtGroup 分区与乘数

| 分区 | 骨骼锚 | 几何 | 伤害乘数 | 附加效果 |
|---|---|---|---|---|
| `head` | `head` | 半径 0.16 m 球（随骨骼）| `CB-HURT-HEAD` = 1.8 | — |
| `torso` | `spine_02`/`chest` | hip→neck 胶囊段，半径 0.28 m | `CB-HURT-TORSO` = 1.0 | 唯一可被护甲覆盖的分区 |
| `limb` | `upperarm*/forearm*/hand*` | 段长 ≤0.32 m 胶囊，半径 0.10 m | `CB-HURT-LIMB` = 0.7 | 不被任何护甲覆盖（GDD：重甲不覆盖四肢）|
| `leg` | `thigh*/calf*` | 半径 0.13 m 胶囊 | `CB-HURT-LEG` = 0.55 | 累计 → `broken_leg`（§3.5）|

分区重叠时按 **head > torso > limb > leg**、同层取**体积最小者**，保证一次命中只有一个乘数。`moveset.hitboxes[].hurtGroup`（10 §1 写 `"body"`）是**作者声明的预期部位**，仅用于调试兜底；**实际乘数一律由受击者骨骼几何决定**，冲突时以几何为准并在 debug overlay 报警——否则数据作者能用 hitbox 声明把全身刷成 head。

### 3.2 护甲覆盖规则

| 护甲类 | 覆盖分区 | 伤害乘数 | 备注 |
|---|---|---|---|
| 无护甲 | — | 1.00 | 基准 |
| 轻型（软甲/防刺）| `torso` | `CB-ARMOR-TAKEN-LIGHT` = 0.85 | 减伤 15% |
| 重型（钢板重甲）| `torso` | `CB-ARMOR-TAKEN` = **0.55** | 减伤 45%；**不覆盖 limb/leg/head** |
| 头盔（可选，GDD 未定）| `head` | `CB-ARMOR-TAKEN-HELMET` = 0.45 | 启用后 head 实际乘数 = 1.8×0.45 = 0.81，仍高于未穿甲的躯干 |

- **口径**：`CB-ARMOR-TAKEN` 是**伤害承受系数**（0.55），不是"减伤 55%"。若 GDD 要 55% 减伤只改这一个数（→0.45），不得在别处补乘数。护甲的移速/噪音负效应由角色属性侧承担（第 05 章）：一个乘数只承担一件事，才能在 §8 单独断言。

### 3.3 是否引入护甲耐久：**不引入**（论证）

| # | 理由 |
|---|---|
| 1 | **撤离玩法已收全额成本**：GDD §3.1「武装突袭」失败即丢失全部带入装备。再来一层耐久，等于同一笔风险收两次费 |
| 2 | **最优解会变成裸奔**：护甲寿命 × 减伤后的期望收益一旦低于携带成本，理性玩家最优策略就是"低于阈值不带甲"，直接反掉 GDD §3.3「军阀残党：钢板重甲硬抗子弹」的流派前提 |
| 3 | **决策性质错位**：耐久把"穿不穿甲"从战术决策变成财务决策，而只有战术决策属于局内战斗管线 |
| 4 | **重复建模**：部位伤害已经是"甲的薄弱面"，耐久是同一问题的第二种表达，叠加后玩家无法从反馈中学习 |
| 5 | **不可回放、不可验收**：耐久消耗发生在局外维修，不属于逻辑步；I5 要求的回放一致性覆盖不了它，第 12 章也无法用黑盒用例表达 |

结论：本框架只提供 `armorTaken`（一个静态乘数）。若未来需要"损耗感"，用**局外维修配方消耗**表达（离线经济，GDD 侧），**永不进入战斗管线**。

### 3.4 闪光 / EMP 硬直：`stun` 是独立通道

| 通道 | 写入者 | 消退 | 锁下半身 | 可被处决 | 备注 |
|---|---|---|---|---|---|
| `hitstun` | `reactions.json` 的 `hitstunMs`（如 220 ms）| 计时到 0 | 否（I4）| 否 | 每次命中写入取 `max` |
| `poise → stagger` | poise 累加 ≥ `CB-POISE-MAX` | `CB-EXEC-STAGGER-WINDOW` 900 ms | **是**（I4 唯一例外）| **是** | §4 |
| `stun`（闪光/EMP）| 道具/技能 | `CB-STUN-FLASH` 1400 ms / `CB-STUN-EMP` 2200 ms | 是 | **否** | 不累加 poise、不受 `CB-POISE-REGEN` 影响 |

三条通道互不覆盖：`stun` 只写 `combat.stunUntilStep`，poise 值保持不变（闪光不能"刷破防"）。**`stun` 期间不可处决**是刻意设计：否则一颗闪光弹 = 一次免费处决，破防窗口（§4）的经济意义被抹掉。

### 3.5 `broken_leg`

单次腿部伤害 ≥ `CB-LEG-BREAK-DMG` = 12，或本局累计腿部伤害 ≥ `CB-LEG-BREAK-TOTAL` = 20 → 置 `broken_leg`（GDD §3.2：击中腿部骨折无法奔跑）。效果只有一条：**拒绝 `jog`/`sprint`/`vault` 输入，最大速度降为 `CC-SPD-WALK` 1.55 m/s**。持续到本局结束或被夹板类道具清除（道具属 GDD 侧，本框架只提供状态与约束）。

## 4. poise 与破防

### 4.1 参数与累加规则

| 项 | 规定 | 常量 |
|---|---|---|
| 上限 / 累加 | `poise += hb.poiseDamage`，`≥ 60` 即破防 | `CB-POISE-MAX` |
| 回复 | 停止受击 **2 s** 后按 12/s 回复：`60/12 = 5 s` 满值回零 | `CB-POISE-REGEN` + `CB-POISE-REGEN-DELAY`（`CB-新增-10`）|
| 破防 | 立即 `stagger`，**poise 清零**并进入免疫期 | — |
| 免疫期 | stagger 全程 + 结束后再 1 s 内不再累加 poise | 派生（`CB-EXEC-STAGGER-WINDOW` + 1 s）|
| 可处决窗口 | 900 ms | `CB-EXEC-STAGGER-WINDOW` |
| 状态表现 | `hit_heavy_front_break`：`hitstunMs` 900、`lockLowerBody: true` | 10 §3 |

「清零 + 免疫期」是 F5 的消除点：只清零不免疫时第二击会立刻再破防，表现为"一直跪着"或"破防了却处决不出来"（窗口被下一次破防重置）。

### 4.2 谁有 poise

| 单位 | poise | 可破防 | 可处决 | 依据 |
|---|---|---|---|---|
| 玩家 | 有（60）| 是 | 是（被敌人处决）| `CB-POISE-MAX` 定义即玩家阈值 |
| 精英人类 AI | 有（角色表可覆盖，默认 60）| 是 | 是 | `ai_roles.json` 的 veteran/brute |
| 普通感染者 | **无（恒 0）** | 否 | 否 | 见下 |

**普通感染者没有 poise、只有 hitstun 的四条理由**：① **状态语义不存在**——破防的定义是"防御姿态被打散、露出可被处决的空当"，感染者没有防御姿态，`stagger` 对它无可读视觉语义。② **破坏席位经济**——`SL-MAX-ATTACKERS` = 2 保证"被围而不被群殴"；若尸群可破防，2 只同时破防就制造出连续处决机会，900 ms 窗口的经济性被清零。③ **预算**——poise 需每单位一个累加器 + 2 s 消退计时，200 只时是 O(n) 每步更新而收益为零，`TM-BUDGET-LOGIC` 只有 3.5 ms。④ **设计意图**——处决是"人与人之间的表演"（人类 AI 有喊话/威胁/撤退），感染者承担数量压力，靠 hitstun 220 ms 打断 + 击退表达，不靠单点突破。

## 5. 处决判定（`combat/execution.ts` 规格）

### 5.1 触发条件（8 条，全满足才可发起）

| ID | 条件 | 判据 | 失败返回 |
|---|---|---|---|
| C1 | 距离 | 水平距离 ≤ `CB-EXEC-RANGE` = 1.35 m（忽略 Y）| `'tooFar'` |
| C2 | 朝向锥 | 玩家 yaw 与「玩家→目标」夹角 ≤ `CB-EXEC-ANGLE`/2 = 35° | `'wrongAngle'` |

数据侧硬约束：`category === 'execution'` 的招式必须满足 `requirements.targetHpPct ≤ CB-EXEC-HP-PCT`（10 §0 第 6 条），否则加载期报错。判定只在玩家按下处决意图的那个逻辑步做一次；不通过即丢弃意图（不进输入缓冲），避免"贴脸狂按忽然弹出处决"。

### 5.2 发起、状态锁定与 `execLock` 保护

发起时同一逻辑步内顺序固定：① 双方 `state → 'locked'`；② 记录快照 `{pos, yaw, hp, poise}` 供中断回退；③ 写 `execLock`；④ 攻击者 action 切为 execution 类招式。`interface ExecLock { partnerId: number; untilStep: number; sourceActionId: number }`，保护窗 = `max(处决动作总时长, CB-EXEC-STAGGER-WINDOW 900 ms)`，下限即 900 ms。

| 层 | 做法 | 效果 |
|---|---|---|
| 槽位层（预防）| `requestSlot` 仲裁前过滤：`req.targetId` 的 actor 带 `execLock` → 该目标**不进候选集**；同时把双方所在槽位置为 `SlotState = 'blocked'`（**复用既有枚举，不新增状态**）| AI 拿不到席位，且 `blocked` 触发 `SL-BLOCK-SHIFT` 让 AI 主动让开而非原地等 |
| 结算层（兜底）| `resolve` 步骤③ 检查 `victim.execLock.partnerId !== attacker.id` → `reason='execLock'` | 已在 active 窗、无法回滚的攻击变成 **0 伤害**，但仍广播 `t:'hit'`（§8 CB-AC-10）|
| 时序与抢占 | `untilStep = step + ceil(保护窗 / TM-DT)`，到期自动失效；两玩家同时满足时按 `actor.id` 升序原子写，先到先得 | 无需额外清理逻辑；I5：结果可复现 |

### 5.3 四类中断原因与回退

| # | 中断原因 | 检测点 | 回退 |
|---|---|---|---|
| 1 | 距离破：被推挤/爆炸击退到 > `CB-EXEC-BREAK-DIST` 1.55 m（`CB-EXEC-RANGE`×1.15）| 每步锚点误差检查 | 双方回 `stagger`（各 200 ms 后摇），不结算处决伤害 |
| 2 | 玩家进入 `stun`（闪光/EMP）| 步骤③ 通道 | 处决失败；目标 HP 恢复到进入时快照值，保留 stagger 剩余时间 |
| 3 | 目标在保护窗内被第三方打死（爆炸等）| `victim.combat.dead` | 处决动作转空挥，玩家进入 `CB-HEAVY-RECOVERY` 460 ms |
| 4 | 目标被第三方抢占处决 | `execLock` 原子写失败 | 本次意图丢弃，玩家回 idle，无惩罚 |

### 5.4 双人动画对齐

进入时用 `rootMotion.mode = 'warp'`（10 §1）把双方拉到锚点对：攻击者 `warpTarget = 'target_chest'`、目标反向对齐攻击者 `hand_r`。**对齐误差 ≤ `CB-EXEC-ANCHOR-TOL` 0.15 m**：每逻辑步用注视/手部 IK 修正剩余偏差（单步上限 0.05 m），超 0.15 m 直接判中断原因 1。锚点用**世界坐标 + 双方 snapshot 的 yaw**，不用动画烘焙的局部偏移——否则不同身高组合（1.78 m vs 矮小感染者）会把手穿进对方胸腔。

## 6. 冻帧与时间缩放

### 6.1 与 03 §2 的关系（契约变更申请）

03 §2 的 M1 实现是 `world.hitstop = N frames` → 冻帧期间**跳过阶段 2–4（全局）**。本章 §6.2 提出替换为 **per-actor 冻帧**，理由：全局跳过会让第三方 AI 在 60 ms 内定格，破坏 I2 的席位轮转与 `SL-UPDATE-HZ` 4 Hz 时序（表现为"整场战斗一顿一顿"）。替换方式：`world.hitstop` 字段**保留**但语义降级为"全局限幅兜底"——仅当同一步内 ≥3 个 actor 同时进入冻帧才置位；主路径改为下节 per-actor 累加器。这是本章唯一一处对 03 的实现层变更，需在 03 下一版同步。

### 6.2 per-actor 冻帧（只冻结受击双方，不冻结整帧）

```ts
// combat/tick.ts 内逐 actor 执行；不跳过任何 fixedUpdate 阶段
if (a.combat.hitstopMs > 0) {
  a.combat.hitstopMs = Math.max(0, a.combat.hitstopMs - TM_DT_MS);  // 局部累加器按逻辑时间扣减
  a.anim.localAcc  = a.anim.localAcc;   // 动画时钟不推进 → 视觉定格在当前帧
  a.combat.actionT = a.combat.actionT;  // 招式时间轴不推进
  a.motor.vel      = a.motor.vel;       // 击退速度不积分
  return;                               // 仅本 actor 返回；其他 actor 与本帧其余阶段照常
}
```

| 冻结（该 actor 内）| 不冻结 |
|---|---|
| 招式时间轴 `actionT`（windup/active/recovery 不推进）| 输入缓冲老化（`CB-INPUT-BUFFER` 120 ms 继续走）|
| 动画时钟（视觉定格在该帧）/ 击退速度积分 | `hitstunMs` 扣减（受击方净硬直 = hitstun + hitstop）|
| poise 消退计时（`CB-POISE-REGEN-DELAY` 不倒数）| 第三方 actor 的一切（槽位、AI、移动）与 `bus.flush` 出队（阶段 11）|

60 ms（`CB-HITSTOP-LIGHT`）= 3.6 逻辑步，100 ms（`HEAVY`）= 6 步，140 ms（`EXEC`）= 8.4 步。**跨补算步必须连续扣减**（`TM-MAX-CATCHUP` 3 步时一次补算会吃掉 50 ms），因此用"按 `TM-DT` 扣减"而不是"按渲染帧计数"——否则掉帧时冻帧时长翻倍，回放不一致（I5）。

### 6.3 处决终结的 0.12 s 慢放

`CB-EXEC-SLOWMO` = 0.12 s、倍率 0.35。**只改视觉时间**，逻辑一步不动：

```ts
// anim/layers.ts（阶段 9，视觉侧）
const visualRate = clip.playRate * (world.slowMoUntilStep > world.step ? 0.35 : 1.0);
animTime += dt * visualRate;   // 动画播放变慢；combat 侧仍 actionT += TM-DT
```

0.12 s 内逻辑推进 `0.12 × 60` = 7.2 步（正常），视觉动画只推进 2.5 步 ≈ 1/3 速度。逻辑步不被拉伸 ⇒ 回放、命中窗口、槽位 tick 全不受影响。慢放与冻帧可叠加，顺序固定：处决命中先吃 `CB-HITSTOP-EXEC` 140 ms 冻帧，再进 120 ms 慢放，总视觉停顿 260 ms。

## 7. 数值接口与撤离玩法衔接

### 7.1 本系统输出的三个伤害字段

| 字段 | 来源 | 量纲 | 消费方 |
|---|---|---|---|
| `damage` | `hb.damage × hitGroupMul × armorTaken × ammoQualityMul` | 生命点数 | `Actor.hp`、HUD、死亡判定 |
| `poiseDamage` / `knockback` | `hb.poiseDamage`（不经部位/护甲修正）/ `hb.knockback × (CB-KNOCKBACK-MASS-REF / mass) × knockbackScale` | 点数（阈值 60）/ m/s | poise 累加器 / `motor.vel` |

```
finalDamage  = round( hb.damage × CB-HURT-* × armorTaken(或 1.0) × ammoQualityMul )   // 下限 CB-DMG-MIN = 1
knockbackVel = hb.knockback × (CB-KNOCKBACK-MASS-REF / mass) × reaction.knockbackScale
```

例：`hb.damage` 22、命中重甲躯干、标准弹 ⇒ `22 × 1.0 × 0.55 × 1.0 = 12.1 → 12`；同一击打腿部 ⇒ `22 × 0.55 × 1.0 = 12.1 → 12`（**重甲对四肢无减伤，但腿部乘数低且会骨折**）——这正是 GDD「低级装备永远有威慑力」的数值形态。

### 7.2 必须由 GDD 侧决定、本框架不擅自定的三个量

| # | 待定量 | 为什么本框架不能定 | 本框架提供的接口 |
|---|---|---|---|
| 1 | **武器基础伤害表**（每武器/每招式的 `hb.damage` 绝对值）| 由经济与武器分级决定（价格/稀有度/弹药消耗），属 GDD §9 调参阀门 | `moveset.hitboxes[].damage` 字段，校验器只查非负与 `poiseDamage ≤ 30`（轻击）|
| 2 | **护甲减伤上限**（`CB-ARMOR-TAKEN` 最终取 0.55 还是 0.45、是否要轻/中/重三档）| 与"重甲移速惩罚 + 破产风险"耦合，属 GDD §3.3 流派平衡 | 表驱动 `armorTaken(class, hurtGroup)`，改表不改代码 |
| 3 | **弹药品质系数 `ammoQualityMul`**（档位与数值，如 0.8/1.0/1.3）| 与弹药经济、搜刮产出直接绑定 | `ammoQualityMul(attacker)` 单点函数 + 默认 1.0，未定义时 debug 警告 |
