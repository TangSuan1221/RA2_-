# 战斗系统框架 · 01 参照系核实与去伪
**这一章的唯一目的：让执行 AI 知道哪些"事实"可以直接照抄，哪些是网络转述、哪些是错的。照错误因果实现，会做出看起来像 TLOU、玩起来不像的东西。**

---

## 0. 为什么必须先做这一步

用户给的四条线索里，只有两条能被一手资料证实（GDC 演讲 + UE5 官方文档），一条被 README 反证（MontageGraph），一条只能作为"引擎考古"参考（OpenGOAL）。

如果执行 AI 按错误前提实现，会发生这些具体的错误：

| 错误前提 | 会做出的错误实现 | 实际后果 |
|---|---|---|
| "槽位是玩家周围 16 个固定点" | 把 16 个坐标算一次就缓存不动 | 敌人永远站同一批点、被墙挡住也不动、看起来像排队 |
| "TLOU2 用运动匹配所以第一作就是" | 把运动匹配当作唯一移动方案，不做状态机兜底 | 无素材时彻底瘫痪（见 04 §1 失败模式） |
| "MontageGraph 是顽皮狗架构复刻" | 照搬它的网络延迟补偿与 GAS 耦合 | 引入网页端不需要的复杂度，且拿不到它的核心收益 |
| "顽皮狗用 GOAL 写 TLOU2" | 试图在本框架引入 Lisp 式脚本层 | 白做一层解释器；参考实现是纯 TS 纯函数 |

## 1. 逐条核实

### 1.1 timofeji/MontageGraph（E1，README 原文）

**证伪**：README 全文未出现 Naughty Dog / The Last of Us / Uncharted 等词。项目自述服务于 **EonBlade**（联机剑斗），取向是 PvP 近战判定一致性，不是 TLOU 式 PvE 战局调度。

**真实可迁移机制（三个，全部已进入本框架）**：

| 机制 | 原文要点 | 本框架落在哪 |
|---|---|---|
| **Collision Caching** | 动画时间轴指定碰撞段，采样后**烘焙碰撞形状到文件**；运行时对**被跳过的帧做回溯检测**（其做法引自 Digital Confectioners） | `08 §2` 回溯命中：hitbox 8 顶点世界坐标环形缓冲 + 上一帧→当前帧 OBB 连续扫掠 |
| authoritative rewind / lag compensation | 用同一份"过去与未来的碰撞体积缓冲"做回滚判定 | 本框架**不采用网络回滚**（单机 + 未来联机另立），但**保留缓冲结构**，因为它同时解决掉帧漏判 |
| AnimMontage 链接做连招 | 以蒙太奇片段为节点连成链，配 blend handle 拖拽 fade | `06 §5` 连招图（`combo.json`）与 `04 §5` 蒙太奇分段 |

**设计哲学统一到一句话**：**编译期缓存数据 + 运行时解释**。这条哲学同时解释了为什么本框架要把动画烘焙成 `*.mmdb`、把碰撞烘焙成顶点快照、把招式写成 JSON 而不是代码。

### 1.2 UE5 Motion Matching / Pose Search（E1，Epic 官方文档全文）

可直接照抄的参数语义（本框架常量 ID 已一一对应）：

| UE 原名 | 语义 | 本框架常量 |
|---|---|---|
| Trajectory / Pose / Heading / Velocity / Phase Channel | Schema 由 Channel 组成，**总代价 = 各 channel 代价之和** | `MM-W-TRAJ` / `MM-W-POSE` / `MM-W-HEADING` / `MM-W-VELOCITY` |
| Sample Rate | 数据库采样率 | `MM-SAMPLE-HZ`=30 |
| Number Of Principal Components | PCA 维数 | `MM-PCA-DIMS`=8 |
| Pose Search Mode: Brute Force / **PCAKDTree** / VPTree | 后两者官方标 experimental | 采用 **PCAKDTree**（`04 §1`），理由=网页端必须省 CPU |
| KDTree Max Leaf Size | 叶子容量 | 16（`04 §1` 建议值） |
| KNNQueryNumNeighbors | **粗筛候选数，之后做全代价精算** | `MM-KNN`=32 |
| Pose Jump Threshold Time | 同一片段内不许跳太近 | `MM-POSE-JUMP-T`=0.25s |
| Pose Reselect History | 最近选过的帧禁止复用 | `MM-RESELECT-T`=0.60s |
| Search Throttle Time | 检索节流 | `MM-SEARCH-THROTTLE`=33ms |
| Use Inertial Blend / Blend Time | 惯性化混合 | `MM-BLEND-T`=0.18s |
| Override Continuing Pose Cost Bias | 鼓励继续播放当前帧 | `MM-CONTINUING-BIAS`=−0.05 |
| Trajectory 权重示例 3.0 vs Pose 1.0 | 官方示例权重 | `MM-W-TRAJ`=3.0 / `MM-W-POSE`=1.0（照抄） |

**去伪**：
- **"运动匹配 = 无状态机"是错的**。UE 官方节点依然有进入条件、notify（`Block Transition`/`Exclude From Database`）与状态机外壳。本框架 `06 §6` 明确保留 Lower 状态机，运动匹配只负责"状态内如何走"。
- **"PCAKDTree 是生产级方案"要打折**。Epic 自己标了 experimental。本框架用它的理由不是"最好"，而是"网页端 CPU 预算只允许这个"（`TM-BUDGET-MM-SEARCH`=1.2ms），并**要求 04 章给出退化为暴力搜索的分界条件**。

### 1.3 GDC 2021《Melee AI in The Last of Us Part II》(Min-Lun Chou)（E1，经中文实录）

这是**唯一**能支撑"顽皮狗式战局调度"的一手依据。四条硬事实：

1. TLOU2 战斗系统建立在 **Uncharted 4** 之上；UC4 攻击预警极短、玩家必须抢先出手才能打断；TLOU2 **拉长了 Attack Tells** 使近战与枪战平级。→ 落点：`CB-TELL-MARGIN`=−80ms（预警必须早于命中 80ms）+ `SL-TELL-SCALE-*` 三档角色预警缩放。
2. **三层数据结构**：**Melee Attack**（选哪一招）/ **Melee Moves**（移动到攻击位）/ 上层 **Melee Behaviors**（按角色类型 + 环境生成攻击指令表，决定接近或保持距离、跑还是走、是否加入战斗）。→ 落点：`10 §1` 的 `moveset.json` = Attack 层；`06 §3` 的"接近相 vs 攻击相" = Moves 层；`10 §5` 的 `ai_roles.melee.attackTable` = Behaviors 层。
3. **Strafe Slots**：槽位坐标位于**以玩家为中心的 16 条延伸线**上，NPC 进入线的**空隙**；延伸线被障碍挡住时，寻路**跟踪被挡的线并改位避开**；到达槽位执行既定动作；系统**自行调整槽位**避免物件阻碍。→ 落点：`09 §4` 的 `buildSlotTable`（16 线 × 3 环 → 障碍剔除 → 相邻线合并成 gap → 每 gap 一槽）+ `SL-BLOCK-SHIFT`=3 步=67.5° 的改位上限。
4. **高位/低位两套近战**：民居场景因房檐/墙/栅栏而复杂化；玩家在齐腰栅栏受高位攻击时身体后仰近乎坠落。→ 落点：`moveset.requirements.heightDeltaMax`=0.60m + `ai_roles.melee.preferHeight` + `06 §4` 环境探针的 `ledge_high`/`ledge_low` 标签。

**去伪**：
- 演讲没有给出任何具体数值（16 线是有了，但环半径、token 数、超时值都没有）。本框架的 `SL-RING-DIST`=1.55/2.35/3.20、`SL-MAX-ATTACKERS`=2 等全部是 **E3 工程估算**，必须在 M6 里程碑用可玩性实验校准（见 12 章）。
- "槽位 = 16 个点"是误读：16 是**线**数，槽位是**线上的间隙**，且每帧（4Hz）可重算。

### 1.4 open-goal/jak-project + NaughtyDog-Debug-Menu-Patch-Tool

| 项目 | 能用什么 | 不能用什么 |
|---|---|---|
| open-goal（E1） | 证明顽皮狗习惯把"行为/状态"写在**脚本层**而非硬编码；GOAL = Game Oriented Assembly Lisp | 不能提供 TLOU 的任何实现；本框架**不引入 Lisp 层**（见下） |
| Debug Menu Patch Tool | 只能证明"官方存在可观测的视锥/寻路/槽位/混合权重调试层" | 需破解主机、非源码；本框架**改用自建 debug overlay**（13 章），观测项按它的类别对齐（视锥、路径、槽位、动画权重） |

**关于"为什么本框架不引入脚本层"**：GOAL 存在的原因是 2001 年在 PS2 上要热重载游戏逻辑。网页端已经有 HMR + JSON 数据驱动，收益重复（`11 §6` ADR 有记录）。本框架的等价物是 **JSON 数据 + 纯函数规则**，这满足"策划改数值不用改代码"的真实需求，且不引入解释器开销。

## 2. 本框架与 TLOU 的真实关系（必须写清楚，防止执行 AI 误解目标）

**本框架不是移植，也不可能移植。** 顽皮狗没有公开 TLOU2 的源码、动画库、AI 数据。本框架是：

> 以 **GDC 公开事实（E1）** 为骨架、以 **UE5 官方运动匹配文档（E1）** 为动画方案、以 **本工作区对 TLOU/神海的逆向研究（`研究\TLOU-REA-大地图与关卡规范.md`）** 为空间与通行尺度、以 **撤离玩法 GDD（E0 需求）** 为约束，独立重建的一套**可判定的技术规格**。

因此"完全复刻战斗系统"的**可交付定义**是（这是 12 章验收的总纲）：

| 维度 | 可判定标准 |
|---|---|
| 战局调度 | 任意时刻同时攻击的 AI ≤ 2；敌人从 16 线间隙进入；被墙挡住的线会改位（`09 §4` 断言） |
| 近战手感 | 攻击预警 ≥80ms 且可读；输入到首帧表现 ≤100ms；TTK 落在表内（`11 §3` 五定律） |
| 上下文处决 | 近墙/桌/窗触发替换动画，锚点对齐误差 ≤0.15m（`06 §4` 断言） |
| 移动表现 | 运动匹配选帧抖动率、滑步量低于阈值（`04 §9` 断言） |
| 镜头 | 无穿墙、无抽搐、定向震动（`07 §8` 断言） |
| 可复现 | 同一 seed + 同一输入序列 → 逐帧状态哈希相同（不变量 I5、`12` E 组） |

**不可交付的部分（诚实声明）**：TLOU2 的动作捕捉素材（数千段手工标定的动画）、面部表情系统、环境叙事、音频设计。这些不在技术框架范围内，素材缺失时按 `04 §1` 的退化路径处理（少量素材也能跑，只是表现力下降）。

## 3. 全局去伪清单（10 条，执行 AI 不得再引用）

| # | 流传说法 | 判定 | 依据 |
|---|---|---|---|
| 1 | MontageGraph 基于顽皮狗经验构建 | **伪** | README 全文无此内容（E1） |
| 2 | TLOU2 是 Motion Matching 的首创者 | **伪** | 该技术更早见于育碧《荣耀战魂》(2017) 等公开分享；TLOU2 是"发扬光大"（E2 业界共识，非 E1） |
| 3 | 运动匹配可以取代状态机 | **伪** | UE 官方节点仍带状态机与 notify（E1） |
| 4 | 槽位 = 16 个固定世界坐标点 | **伪** | 16 是延伸线数，槽位是间隙且 4Hz 重算（E1） |
| 5 | 顽皮狗用 GOAL 写 TLOU2 | **无证据** | GOAL 是 Jak 时代（PS2）的语言（E1 只覆盖 Jak） |
| 6 | "相变同步 Phase Matching"是顽皮狗专有术语 | **无证据** | 业界通用相位匹配；UE 把它做成 Phase Channel（E1） |
| 7 | 必须有物理引擎才能做角色移动 | **伪** | 本框架自建胶囊求解（`05 §3`），理由=确定性与回放（`11 §6` ADR-01） |
| 8 | 网页端跑不动运动匹配 | **半伪** | 6000 帧 × 8 维 PCA + KDTree 可在 1.2ms 内完成（`02 §4` 预算）；跑不动的是"暴力全库逐帧全姿态比对" |
| 9 | 敌人 AI 越多越难越好 | **伪** | 本框架用 token 上限硬约束（不变量 I2），难度靠 token 数与 tellScale 调，不靠堆量 |
| 10 | 手感靠"多调几遍" | **伪** | 手感=可翻译成毫秒/米/度的参数集（`11 §1` 映射表 20 条） |

## 5. 本章给执行 AI 的三条硬指令

1. **凡 E3 数值，实现时必须做成可外部改的常量**（`config/constants.ts` 单一导出），不得内联到逻辑里。E1 数值（如 16 线、80ms tell、30Hz 采样）可硬编码但必须在注释标注 `// E1 S1`。
2. **凡本章"去伪清单"里的说法，一律不得写进代码注释或提交说明**，避免后续维护者被误导。
3. **素材缺失时不要绕过断言**：`04 §1` 的退化路径允许"少素材跑通"，但 `12` 章的验收用例必须全过；不允许通过降低断言来"跑通"。
